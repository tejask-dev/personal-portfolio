01 / Connected-app reliability

Getting past the consent page.

Navigation correction deployed

The server reported success, but the person was still stuck on the consent page. We needed to test whether the browser could reach the provider's sign-in page and retry without starting a new authorization.

My part

I made this failure a priority and brought in what I saw on my phone. I required a browser test before release. Claude and Codex did the diagnosis, fix and review, and I later checked a Gmail retrieval task myself.

The decision

Keep the existing consent and expiry when retrying the saved provider attempt. Test the whole browser redirect path, including the step the first test missed.

Explanatory walkthrough / no account connection

Browser arrival unproven

A green response was not the destination.

The server returned a successful redirect, but the browser still stopped before provider sign-in. A fixture ending at the first hop missed the real failure.

Sign-in navigation verified

Follow the path a person actually takes.

The corrected flow preserved consent and reached the provider's sign-in page. The release test stopped before granting a real account.

Existing attempt reused

Resume the attempt. Keep its boundaries.

Back, reload, and retry reused the existing provider attempt. Retry did not create a fresh authorization or extend its lifetime.

What worked

The navigation fix was deployed and checked through the Google and Notion sign-in screens. Separately, I reported one Gmail read-and-summary task that worked.

What these tests don’t show

Those checks cover one repaired navigation path. They don't show that every connector, phone flow or write action works.

02 / Private AI workflows

A brief from one source you chose.

Locally validated prototype

We wanted a work-preparation prototype that could turn one source you picked into a brief you could check. It couldn't quietly pull in your personal memory or whole inbox, or assume permission to act.

My part

I approved the flow from choosing a source to reading the brief, including the rules for consent, spending, cancellation and keeping data. Claude and Codex split the backend, web and integration work. The pieces were reviewed independently before we joined them.

The decision

Only process the source the person picked, while they still allow it. Check every model request against the spending limit. Discard results that arrive after they've cancelled or withdrawn consent.

03 / Browser-agent privacy

Check what reaches the model.

Locally validated repair

Hiding a protected field in the answer is too late if its value already went into a model request. I wanted the checks where the browser first reads and captures the data.

My part

I required protected-field checks using synthetic test values in the actual outgoing requests and logs. AI agents implemented and reviewed the changes against the existing browser workflows.

The decision

Keep protected values out while allowing the workflows a person has consented to. If the change breaks something, fix it. Don't rewrite old tests just to make the new check pass.

The test checked for synthetic protected values in the outgoing model-request data. This illustration explains that check; it does not run a live security test.

What worked

Tests in a real browser, plus a smaller check on the installed extension, covered how protected fields were read and what reached the model. The final recorded checks passed for those cases.

What these tests don’t show

These checks used synthetic data in a limited setup. They don't prove credentials are safe everywhere. I'm leaving private diagnostics out, and I can't claim every browser or native surface was covered.
